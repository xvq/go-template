# Repository conventions

- Read README.md and docs/development.md before changing architecture.
- This is a pure API template: Fiber v3, GORM/MySQL, Redis sessions, go-playground/validator, optional Asynq. Do not add end-user business, a frontend, RBAC, or another framework without a request.
- Keep application code in internal/app/<app>/{handler,request,service,resource,middleware}; register routes explicitly in routes.go. Handler order matters: middleware first, final handler last.
- Application services own business rules and return models/business results; resources own JSON field selection and never query the database. Keep reusable capabilities in internal/service/<capability>, separate from application business services. Use util/query.Page[T] for service pagination; util/query.Paginate performs Count and page queries and returns Page{Data, Pagination} with complete metadata; Resource.Page only maps Data and preserves Pagination. query.Paginate validates page/size ranges and returns apperror.ErrInvalidPagination before querying. HTTP request.Pagination parses integers/applies defaults and validates the same ranges immediately; keep query-layer validation for non-HTTP callers; the shared error handler maps this error to HTTP 400 (invalid_pagination).
- Resources transform database results. Compose responses such as login directly in handlers. Keep business resource output types private (with exported JSON fields). Define each resource with a private stateless type and transform method, and expose a shared read-only entry using resource.New(type{}.transform). Use its Item/Collection/Page methods; do not add per-resource wrappers. Name resource files and entries after singular table names (admin.go/AdminResource, admin_login_log.go/AdminLoginLogResource, setting.go/SettingResource). Item accepts a model pointer and returns nil for missing associations. Nested mappings call other resource entries, with associations loaded in services; avoid recursive cycles.
- Keep framework packages bootstrap/config/infrastructure/testutil/request/response/resource under internal/core. The core root package exposes globals; lower-level factories/config must not import core or business packages.
- Initialize process-wide Config/DB/Redis/Session/Log/HTTP/Queue explicitly in bootstrap and access them through internal/core; do not inject these through business constructors. Session is prepared automatically with Redis, shares its connection pool, and has no separate Options flag or Close. Treat globals as read-only after startup, never store request state/query chains/transactions in them, and never connect via init. Bootstrap owns cleanup through defer Resources.Close after requests/workers stop; business code must not close shared clients. Keep concrete business service construction in application routes, not bootstrap.
- Use real context.Context from c.Context() in services; never retain pooled fiber.Ctx. Streaming has a separate bounded lifecycle; see response.Stream.
- Keep small shared helpers under internal/util/str and internal/util/query; do not add a catch-all utils package.
- Keep original GORM query capabilities. No generic repository layer just to wrap CRUD. Use explicit updates for zero values. Always handle query errors.
- No AutoMigrate in application startup. Add versioned SQL migrations, do not edit released migrations. AutoMigrate is allowed only for isolated integration-test fixtures.
- Queue is disabled by default. No queue side effects when disabled. Business idempotency/outbox/compensation belongs to downstream projects, not this template.
- Passwords/tokens/SQL parameters/request bodies must not enter logs. No real credentials in tracked files.
- Each command declares required resources with bootstrap.Options (Name/Database/Redis/HTTP/Queue) in its execution code. Open validates and initializes only selected resources; server/schedule commands validate their own non-resource configuration before startup. Help must work without config or services. Settings uses stateless package functions (String/Bool/Int/Strings/Set/Update/List/ClearCache), not injected service instances; preserve validation and cache consistency.
- Keep internal/core/infrastructure/cli/root.go limited to root options and explicit command registration. Business commands belong in internal/command with register.go; they must not import cli. Put each standalone command in its own file; related subcommands such as migrate stay together. Initialize resources only when executing a command.
- Keep the scheduler engine and Task type in internal/core/infrastructure/scheduler; it must not import concrete tasks. Register scheduled tasks explicitly in internal/schedule/register.go, with each task in its own file. heartbeat.go is a removable example task; keep its registration explicit.
- Run gofmt, go test ./..., and go vet ./... for Go changes. Tests replacing globals must run serially and restore them after stopping background work; do not use t.Parallel. Add tests for important rules and fixes as useful, not to chase coverage or mirror simple CRUD. For integration changes, run the documented opt-in tests against disposable services; distinguish skipped tests from passed tests.
- Keep README and API/development docs consistent with behavior. Do not push or create commits unless asked.

- Request structs live in application request packages and use validate tags plus label display names. Shared internal/core/request route wrappers bind and validate before invoking handlers; ID/Pagination are on-demand request helpers. The validator engine lives in internal/core/infrastructure/validator and is explicitly initialized at HTTP/CLI execution startup, immutable afterwards. Use built-in validation rules (username: alphanum, 3–64 characters; passwords: 6–30 Unicode code points, unrestricted content). Use Argon2id for password hashing, without legacy compatibility; business/database rules remain in services. Admin updates require the complete form (nonempty display_name and required enabled, including false); do not implement partial update semantics. Keep JSON field keys in errors separate from translated labels.

- This project is a template under development. Changes do not require historical compatibility; do not add legacy adapters or migration branches unless explicitly requested.

- Admin request bodies use JSON only: omit form tags on application request structs and register body handlers with request.JSON. Use query/form tags and matching wrappers only for endpoints explicitly requiring those sources.

- Admin authentication is Redis-only: Auth() verifies the session/realm and stores only the ID in Locals; handlers use CurrentID and load models on demand. Do not add auth_version or per-request database status checks. Password changes/resets and enabled-state changes/deletion revoke all Redis sessions; propagate revocation failures. Password verification and update must share a transaction row lock (SELECT FOR UPDATE). Redis and DB changes are not a distributed transaction.

- Redis keys use fixed names for their purposes; independent projects use separate Redis databases or instances. Integration tests require an exclusive initially empty Redis DB (default 15, configurable with GOTEMPLATE_TEST_REDIS_DB), and clean up their test data afterwards; never run concurrent suites against the same test DB.

- Settings definitions live in internal/service/settings/definitions.go. Use strict string/boolean/integer/string_array types and optional per-setting validation. Cache complete snapshots in the permanent Redis Hash settings with JSON-encoded field values; settings:version is a permanent generation counter. Version-guarded Lua fills and version-increment-plus-delete invalidation must be atomic. No cache TTL or Sensitive mechanism. Lists include effective value and code default. settings:clear-cache only initializes Redis and reuses ClearCache. Propagate post-commit invalidation failures after bounded retry; reads may fall back to MySQL.
